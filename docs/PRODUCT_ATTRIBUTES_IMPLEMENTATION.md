# Расширенные характеристики товаров — этап 1

Реализовано локально 12 сентября 2026 года. Фильтры реализованы следующим этапом: [CATALOG_FILTERS_IMPLEMENTATION.md](CATALOG_FILTERS_IMPLEMENTATION.md). Импорт каталога остаётся следующим шагом. Источники и примеры собраны в [PRODUCT_DTO_CATALOG.md](PRODUCT_DTO_CATALOG.md).

## Что добавлено

- Все категории: бренд отдельно от производителя, подарочная упаковка и её тип.
- Вино и игристое: регион, аппелласьон, крепость, сортовой состав с долями, ароматы, вкус, гастрономические сочетания, выдержка, производство, температура подачи, профиль вкуса, стиль, потенциал хранения и аэрация.
- Игристое: дополнительно год урожая, статус винтажа и метод производства.
- Крепкие напитки: общие характеристики, стадии выдержки, способы подачи и именованные вкусовые оценки.
- Виски: тип, стиль купажа, число компонентов, заявленный возраст и статус возраста.
- Коньяк: возрастная классификация, заявленный возраст, сортовой состав и зона происхождения.

`spirit` остаётся одной категорией. `subcategory` определяет допустимый блок: `whiskyDetails` для виски или `cognacDetails` для коньяка. Админка показывает соответствующие поля; сервер отклоняет несовместимые блоки.

## Контракт API

Существующие URL, обязательные поля и структура основных характеристик сохранены.

Чтение товара: `brand` и `packaging` на верхнем уровне; новые характеристики категории включены непосредственно в `details` рядом с прежними полями. Например, `details.region`, `details.grapeComposition`, `details.whiskyDetails`. Дополнительной обёртки `details.extendedDetails` в ответе нет.

Запись товара: `brand`, `packaging` и `extendedDetails` передаются на верхнем уровне рядом с прежними полями запроса. Пример **фрагмента** запроса для вина (остальные обязательные поля нужно передать как прежде):

```json
{
  "brand": { "code": "paddle_creek", "label": "Paddle Creek" },
  "packaging": { "giftBox": false, "type": null },
  "extendedDetails": {
    "region": { "code": "marlborough", "label": "Мальборо" },
    "strength": 12.5,
    "grapeComposition": [
      { "grape": { "code": "sauvignon_blanc", "label": "Совиньон блан" }, "percent": 100 }
    ],
    "grapeCompositionComplete": true
  }
}
```

Коды примера должны сначала существовать в соответствующих справочниках.

Семантика обновления новых групп:

- Поле `brand`, `packaging` или `extendedDetails` отсутствует в запросе — сохранённое значение не меняется. Старые клиенты сохраняют новые данные.
- Явный `null` очищает группу.
- Переданный объект полностью заменяет соответствующую группу. Внутри `extendedDetails` нет частичного слияния: для изменения одного свойства нужно передать всю сохранённую группу.
- В новых списках `null` — неизвестно, `[]` — значений нет. Ноль и `false` сохраняются как значения.
- Если у вина задан `grapeComposition`, из него формируется прежнее поле `grapes`. Сортовой состав становится источником названий сортов. У игристого список `grapes` вычисляется из нового состава при чтении.

Модели: backend `CatalogAttributes.java`, admin `src/api/products/attributes.ts`, storefront `src/services/products/interfaces/attributes.ts`.

## Проверки данных

На сервере проверяются диапазоны, обязательные части заполненных объектов, допустимые значения и вложенные списки. Полный сортовой состав требует известных долей с суммой 100%; частичный допускает неизвестные доли, но известная сумма не превышает 100%. Повторы сортов, стадий и измерений вкуса запрещены.

Год игристого согласуется со статусом винтажа. Заявленный возраст виски обязателен при `stated` и отсутствует при `nas`/`unknown`. При `not_aged` нельзя передать срок и ёмкости выдержки. Вкусовые оценки содержат источник и известные границы шкалы; неизвестная шкала допускается без выдуманных границ. Диапазоны выдержки сохраняют включённость границ.

Админка проверяет заполненные группы перед отправкой и показывает ошибки у соответствующих полей. Сервер остаётся окончательным источником валидации.

## Справочники

Только для администратора:

- `GET /api/v1/admin/products/attribute-references/{kind}` — список `{code, label}`.
- `POST /api/v1/admin/products/attribute-references/{kind}` — создать `{code, label}`.

Поддерживаемые `kind`: `brand`, `packaging`, `region`, `appellation`, `grape`, `aroma`, `flavor`, `food_pairing`, `style`, `vessel`, `wood`, `previous_contents`, `serving`, `sensory_dimension`, `whisky_type`, `blend_style`, `age_classification`, `origin_area`, `sparkling_method`.

Код: 1–80 символов, строчные латинские буквы, цифры, `_`, `-`; первый символ — буква или цифра. Подпись: до 160 символов. Код и подпись уникальны внутри вида справочника; подпись сравнивается без учёта регистра. Запись товара требует существующего кода и точной канонической подписи. Создание доступно прямо из поля выбора в админке. Автоматическое заполнение справочников данными источников ещё не выполняется.

## Хранение и обновление сервера

Новые группы хранятся в nullable `jsonb`: `product.brand`, `product.packaging`, `wine.extended_details`, `sparkling_wine.extended_details`, `spirit.extended_details`. Java-модели типизированы и валидируются перед сохранением; JSONB позволяет расширять необязательные характеристики без добавления десятков колонок. Для этапа фильтров потребуются запросы по этим полям и индексы под фактические условия поиска. Справочники хранятся в `catalog_attribute_reference`.

Порядок выкладки:

1. Сделать резервную копию рабочей БД обычным способом проекта.
2. На существующей БД выполнить `infrastructure/db/migrations/20260912_product_attributes.sql` через `psql` с параметрами подключения к нужной БД и `ON_ERROR_STOP=1`.
3. Пересобрать и запустить backend, затем admin frontend из compose-каталога backend.
4. Открыть существующий товар: прежние поля должны сохраниться, новые — быть пустыми. Создать справочное значение, заполнить характеристику, сохранить и повторно открыть карточку.

Миграция добавляет поля без удаления или преобразования прежних данных; повторное выполнение допустимо. В проекте нет автоматического запуска этих SQL-файлов. `ddl-auto=update` не заменяет миграцию: в SQL также задан уникальный индекс по подписи без учёта регистра. Новый backend следует выложить до новой админки.

## Проверки

Backend, из его каталога:

```sh
./mvnw -Dtest=CatalogAttributesTest,CatalogWriteCompatibilityTest,CatalogReferenceTest test
```

Отдельный интеграционный тест PostgreSQL запускается только при явном параметре `catalog.postgres.url`. Ему нужна **новая пустая временная БД**: он создаёт таблицы-фикстуры, дважды применяет реальную миграцию, проверяет сохранность старой строки и чтение/запись типизированного JSONB всех трёх категорий через Hibernate. Он не поднимает весь Spring-контекст и не заменяет проверку выкладки приложения.

```sh
./mvnw -Dtest=CatalogAttributesPostgresTest \
  -Dcatalog.postgres.url=jdbc:postgresql://127.0.0.1:55439/catalog_attributes_test \
  -Dcatalog.postgres.user=YOUR_LOCAL_USER test
```

Admin frontend:

```sh
node --test tests/catalog-attributes.test.cjs
npm run build
```

Для проверки формы без реальных запросов к каталогу: запустить Vite и открыть `/tests/attributes-preview.html`. Фикстура подменяет справочники в своей странице, показывает отправляемый JSON и ошибки. Она не включена в production entry point. Проверены выбор и создание справочника, переключение виски/коньяк, вложенный состав и ошибка незаполненного сорта.

Storefront: `./node_modules/.bin/tsc --noEmit --incremental false`. Добавлены фильтры и вывод заполненных новых характеристик на странице товара, включая вкусовые оценки 1–5; пустые поля скрываются.

Результат локальной проверки: 9 целевых backend-тестов, 1 отдельный тест PostgreSQL, 5 тестов преобразования формы, сборка админки и проверка типов витрины прошли. Полный набор Spring-интеграционных тестов этим прогоном не покрыт. Дополнительный запуск ESLint на новых файлах остановился на TypeScript-синтаксисе: существующий `eslint.config.js` включает `.ts/.tsx`, но не настраивает TypeScript-парсер. TypeScript-компилятор проверку прошёл.
